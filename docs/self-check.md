## Три підсумкові числа

1. Виконано пунктів чекліста: **13 із 20 = 65 %** (6 «частково», 1 «ні»).
2. Покриття бібліотеки `CafeOrders.Core`: **94,6 % рядків, 87,3 % гілок**.
3. Залишковий технічний борг: **6,5 години** (пункти 3, 4, 9, 11, 14, 15; пункт 19 не виправляється
   переписуванням історії).

## Непокриті гілки бібліотеки логіки

| Місце | Гілка | Чому не покрито |
|---|---|---|
| `CafeDesk`, конструктор | `?? throw ArgumentNullException` для 4 залежностей | Перевірка контракту для програміста: композиційний корінь і тести завжди передають об’єкти; тест перевіряв би мову, а не правило |
| `BillCalculator`, конструктор | `?? throw` для `serviceCharge` | Та сама причина — запобіжник від помилки збирання об’єктів |
| `OrderService.Cancel` | `catch (IOException)` із записом `Error` і повторним киданням | `InMemoryOrderRepository` не кидає `IOException`; щоб покрити, потрібен стаб сховища зі збоєм — внесено в борг пункту 14 |
| `ServiceChargePolicy`, рядки 9–18 | Оголошення `const` позначено як непокриті рядки | Особливість coverlet: константи підставляються компілятором і не виконуються; гілок у цих рядках немає |
| `PricingRules` (0 %) | Лише константи | Та сама особливість — клас без виконуваного коду |
| `DocumentTotalCalculator.VolumeDiscountOf`, `CouponDiscountOf` | Середня знижка й фіксований купон нижче порогу | Код ЛР3: тести ЛР3 перевіряють межі великого замовлення й купона знижки; проміжний рядок таблиці не додано |
| `Billing/Bill.CalculateTotal`, рядки 137–140 | `total < 0` після фіксованої знижки за кількість рядків | Можливо лише для рахунку з багатьма дуже дешевими рядками, сума яких менша за фіксовану знижку; характеризаційні тести ЛР6 такого випадку не містять, тест не додано свідомо — клас не використовується касою |
| `InMemoryOrderRepository.GetById` | Повернення `null` для відсутнього номера | Сценарій «замовлення не знайдено» тестується на `FakeOrderRepository` і `CafeDesk`, а не на цьому класі ЛР4 |
